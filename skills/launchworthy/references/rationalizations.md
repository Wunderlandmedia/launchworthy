# Anti-Rationalization Table

When the audit finds a blocker, the natural human move is to talk yourself out of fixing it. That instinct is strongest exactly when the finding is most expensive, because expensive fixes feel inconvenient. Use this table when the user pushes back. Name the excuse, give the counter, then let them decide with the real risk in front of them. Do not argue past a clear "I understand and I am choosing to ship anyway." Your job is honesty, not control.

| The excuse | The reality |
|---|---|
| "It's just an MVP / demo." | An MVP with real signups is a real product to the person whose data is in it. The RLS-off table does not know it is an MVP. Attackers scan for it the same day you deploy. MVP is a reason to keep features small, not a reason to skip auth. |
| "I'll add auth / RLS later." | "Later" usually means "after the first user, or the first breach." Turning on RLS after you have live data means writing policies without locking anyone out mid-session, which is harder, not easier. The cheapest time to do it is now, before there is data to leak. |
| "No one will find it." | Bots find it. Public endpoints, exposed Supabase projects, and open Firebase databases are indexed and scanned continuously. "Nobody knows my URL" is not a security control. You are not too small to be scanned; scanning is automated and free. |
| "It works fine for me." | You are one user on fast wifi with a warm cache and no malice. Production is a hundred strangers on bad connections, one of whom is curious about what happens if they change the ID in the URL. "Works for me" is the starting line, not the finish. |
| "I don't have time to fix all this." | You do not have to. The punch list is ranked. Fix Now is usually two or three things and often under an hour with the playbooks. The point of the ranking is exactly so you can ship safely without doing everything. |
| "The AI tool that built it wouldn't ship something insecure." | AI coding tools optimize for a working demo, not a hardened deployment. They leave RLS off, secrets in the client, and no rate limits by default, because those make the demo work faster. That gap is the entire reason this audit exists. |
| "Supabase / Firebase handles security for me." | They give you the tools; they do not turn them on. Supabase ships with RLS off unless you enable it. Firebase ships in test mode that expires into either open or closed. The platform is secure; your configuration is what is not. |
| "The API key is fine, it's meant to be public." | Sometimes true (Supabase anon key, Firebase config) and sometimes catastrophic (service_role key, an admin token, a Stripe secret). The key being public is only safe if the layer behind it (RLS, Rules, server-side checks) actually restricts what that key can do. If that layer is missing, "it's meant to be public" is how the breach happens. |
| "I'll deal with backups if something breaks." | The moment something breaks is the one moment you cannot make a backup. Recovery is the one thing that has to exist before the incident, not after. An untested backup counts as no backup until you have restored from it once. |
| "Rate limiting is premature optimization." | Rate limiting is not about scale, it is about abuse. One script hitting your AI endpoint overnight is a four-figure bill, not a performance problem. On paid and auth endpoints it is a cost and security control, and it belongs in v1. |
